# Спецификация: acquisition path в прошивке репитера MeshCoreTel

**Статус:** Draft v0.1
**Дата:** 2026-09-06
**Аудитория:** агент, дорабатывающий прошивку репитера (ветка `vbart-meshcoretel`).
**Родительская спека:** `docs/MeshSMO-Sensors-IMPLEMENTATION_SPEC.md` (см. §7.1.3 и Risk A).

---

## 1. Проблема

Репитер MeshCoreTel (прошивка `v1.16.0-vbart-meshcoretel-v1.2.0`) в текущем виде предоставляет:

- HTTP: `POST /login`, `POST /api/command` (CLI), `GET /api/stats[?series=...]`;
- CLI-команды: `ver`, `clock`, `advertise`, `sensor list [start]`, `stats-core`, `stats-radio`, `stats-packets`.

Ни CLI, ни HTTP **не позволяют инициировать произвольный binary request к удалённой ноде MeshCore** и получить её ответ. Из-за этого MeshSMO Sensors Gateway может собирать только телеметрию самого репитера; опрос pull-only LoRa-датчиков (метеодатчики, передающие ответ на запрос) невозможен.

## 2. Цель

Добавить в прошивку репитера возможность **по запросу из CLI или HTTP отправить бинарный payload конкретному контакту (по 32-байтному публичному ключу) через LoRa-эфир и вернуть ответ этой ноды**.

Формат самого payload прошивка не интерпретирует — она лишь транспорт. Семантика (envelope PollRequest/PollResponse) определена в `MeshSMO-Sensors-IMPLEMENTATION_SPEC.md` §7.3 и реализуется на стороне датчика и Gateway.

## 3. Не-цели

- Не реализовывать разбор протокола датчиков в прошивке.
- Не менять существующие эндпоинты, команды и форматы ответов (обратная совместимость обязательна).
- Не делать очередь/retention сообщений в прошивке: ровно один in-flight request, ответы вне окна ожидания отбрасываются.

## 4. Требования к функциональности

### 4.1. Общая логика

1. Вход: публичный ключ получателя (32 байта, hex-строка 64 символа) + бинарный payload (raw байты) + таймаут ожидания ответа.
2. Прошивка отправляет payload как **direct message с raw binary content** получателю (тот же путь, каким Companion app отправляет данные ноде; в MeshCore это direct packet c типом содержимого, отличным от обычного текста — использовать примитив отправки, доступный в кодовой базе прошивки для companion data; текстовая кодировка/шифрование — штатные механизмы MeshCore).
3. Прошивка ожидает **direct-ответ от этого же отправителя-получателя** в течение окна ожидания. Входящие прямые пакеты от других нод в этом окне для данного request'а игнорируются (но не ломают обработку обычного трафика репитера).
4. По истечении окна (или при получении ответа) результат возвращается вызывающему: статус + ответные байты (hex) + метаданные приёма (RSSI, SNR — если доступны от radio driver на момент приёма пакета).

### 4.2. Ограничения

- **Один in-flight request на репитер** (LoRa-эфир и так полудуплексный). Повторный вызов во время активного окна → ошибка `Busy`.
- Максимальный размер payload — ограничение прямого сообщения MeshCore (для текущей длины заголовков принять **не более 160 байт**; если в кодовой базе константа меньше — использовать её). Превышение → `PayloadTooLarge`, не обрезка.
- Окно ожидания: 1–30 секунд, по умолчанию 10 с. Значение вне диапазона → `InvalidTimeout`.
- Между завершением окна и началом нового request — без минимальной паузы (backoff — ответственность Gateway).
- Не логировать payload'ы на уровне Information (только Debug с лимитом размера), не логировать токены/пароли (уже так — сохранить).

### 4.3. HTTP API

Аутентификация — как у остальных `/api/*`: заголовок `X-Auth-Token` после `POST /login`.

```text
POST /api/request
Content-Type: application/json

{
  "destination": "<64 hex chars, публичный ключ ноды>",
  "payload":     "<hex, 1..160 байт>",
  "timeoutMs":   10000
}
```

Ответы:

```text
200 OK
{
  "status": "ok",              // ok | timeout | error
  "responseHex": "<hex>",      // null при timeout
  "rssi": -92.0,               // float, null если недоступно
  "snr": 9.5,                  // float, null если недоступно
  "elapsedMs": 812
}

400 Bad Request   { "error": "InvalidDestination" | "InvalidPayload" | "PayloadTooLarge" | "InvalidTimeout" }
409 Conflict      { "error": "Busy" }
503 Service Unavailable { "error": "RadioUnavailable" }   // radio не инициализирован
```

Семантика:

- запрос синхронный: HTTP-ответ приходит после завершения окна ожидания (таймаут HTTP на клиенте будет 15–30 с — это нормально);
- `timeout` — это «пакет отправлен, ответ не получен за окно» (нормальный исход, не ошибка HTTP);
- повторная отправка того же тела запроса после `timeout` — допустима и не является дубликатом на уровне прошивки (дедупликация — ответственность вызывающего через `RequestId` внутри payload).

### 4.4. CLI-команда

Тот же функционал для serial-консоли (формат существующий: команда завершается `CR`, ответ после маркера `->`):

```text
req <destination-hex> <payload-hex> [timeout-seconds]
```

Ответ (одной строкой после маркера, парсится Gateway'ем как обычный CLI reply):

```text
-> OK resp=<hex> [rssi=<float>] [snr=<float>] elapsed=<ms>
-> TIMEOUT elapsed=<ms>
-> ERR <code>          // Busy | InvalidDestination | InvalidPayload | PayloadTooLarge | InvalidTimeout | RadioUnavailable
```

Правила:

- пустой `resp=` при timeout не выводится; строка `TIMEOUT` — успешный синтаксис ответа, не ошибка парсинга;
- `<payload-hex>` до 320 hex-символов (160 байт); суммарная длина команды может превысить существующий CLI-буфер 191 байт — **буфер строки ввода для этой команды нужно расширить** (минимум 420 байт) либо реализовать двухстрочный ввод `req <dest> <len>\n<hex>`; выбрать один вариант и зафиксировать в ответе на эту спеку;
- команда не блокирует консоль дольше окна ожидания.

### 4.5. Таблица состояний и ошибок

| Код | Когда |
|---|---|
| `InvalidDestination` | не hex/не 64 символа/неизвестный контакт |
| `InvalidPayload` | нечётный hex, пустой payload |
| `PayloadTooLarge` | > максимума из §4.2 |
| `InvalidTimeout` | timeout вне 1–30 с |
| `Busy` | уже есть активный request |
| `RadioUnavailable` | radio не готов (init failure, sleep) |
| `timeout` (статус) | отправка прошла, ответа не было |

Отправка не удалась на уровне radio (queue full и т.п.) → HTTP `503 RadioUnavailable` / CLI `ERR RadioUnavailable`.

## 5. Критерии приёмки

1. Обратная совместимость: все существующие команды CLI и эндпоинты работают как раньше (`ver`, `sensor list`, `/api/stats`, пагинация `... next:`).
2. Эхо-тест: два репитера/ноды в одной сети — A делает `POST /api/request` к B, B отвечает заранее заданным binary payload (для теста достаточно временно прошить B тестовым обработчиком или использовать существующий механизм телеметрии ноды, если он отвечает на data request) — получаем `200 OK` с `responseHex`, rssi/snr не null.
3. Таймаут-тест: запрос к ноде в эфире, которая не отвечает, → `status: "timeout"` за ~`timeoutMs` ± 1 с, HTTP 200.
4. Busy-тест: два параллельных запроса → второй получает `409 Busy`.
5. Валидация: некорректный hex/длина → 400 с точным кодом ошибки.
6. Во время активного request обычный функционал репитера (ретрансляция пакетов, `/api/stats`, `sensor list`) не деградирует.
7. Память: request-контекст статичен (одна структура), без heap-фрагментации от повторных вызовов; payload-буферы фиксированные.

## 6. Интеграция с Gateway (что будет использовать MeshSMO Sensors)

Это уже реализовано на стороне Gateway и не требует действий прошивки — просто фиксируем ожидаемый контракт:

- Gateway держит **не более одного** параллельного запроса (совпадает с §4.2);
- Gateway повторяет запрос после `timeout` согласно собственной retry-политике (maxAttempts=2, из registry датчика);
- `responseHex` прогоняется через парсер binary-протокола датчиков (spec §7.3); `rssi`/`snr` пишутся в `measurement_samples`;
- CLI-вариант будет использоваться Serial-транспортом Gateway: ответ `-> OK resp=...` парсится существующим `RepeaterSerialResponseParser` (требование §4.4 — одна строка — критично).

## 7. Открытые вопросы (решить при реализации)

1. Какой примитив отправки direct binary message доступен в кодовой базе прошивки (тот же, что Companion app → нода)? Если direct-канал к off-graph ноде требует предварительного `contacts` — как зарегистрировать контакт по pubkey без полного ключа шифрования (MeshCore direct messages шифруются shared secret пары ключей; репитер знает только pubkey получателя — отправка потребует session/channel-механики, см. вопрос 2).
2. Шифрование: payload датчик ожидает зашифрованным тем же механизмом, каким датчик расшифрует (channel key или ECDH пары). Требование к реализации: поддержать оба режима — (a) отправка в channel с общим ключом, (b) direct по паре ключей, если репитеру доступен механизм обмена. Выбранный режим зафиксировать и отразить в ответе на спеку; Gateway'ю достаточно «payload in → response out».
3. Нужен ли отдельный `/api/cancel` для досрочного завершения окна — на v1 не делаем, окно ≤ 30 с.
